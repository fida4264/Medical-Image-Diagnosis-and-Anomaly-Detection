## 2. Regression Count Reconciliation (Audit 2)

### 2.1 The Discrepancy Investigated
The Phase 9 completion report (`V2.0_PHASE9_PIPELINE_INTEGRATION_QUALITY_GATES_REPORT.md`, Section 9) presented the following regression test table:
- Baseline: 18 tests
- Label reconstruction: 14 tests
- Phase 6: 8 tests
- Phase 7: 15 tests
- Phase 8: 27 tests
- Phase 9: 68 tests
- Total: 150 tests

Earlier Phase 8 project records reported **23 Phase 8 tests** and **64 cumulative tests** for Phases 5–8.

### 2.2 Forensic Repository Findings
An automated collection and execution of all V2 test files in the repository using `python -m pytest <test_files> --collect-only -q` and `python -m pytest <test_files> -v` revealed the ground truth:

```
tests/test_v2_baseline.py:              18 tests (PASSED)
tests/test_v2_label_reconstruction.py:  18 tests (PASSED)
tests/test_v2_phase6.py:                 8 tests (PASSED)
tests/test_v2_phase7.py:                15 tests (PASSED)
tests/test_v2_phase8.py:                23 tests (PASSED)
tests/test_v2_phase9.py:                68 tests (PASSED)
---------------------------------------------------------
TOTAL REPOSITORY TESTS COLLECTED:      150 tests (150 PASSED, 0 FAILED, 0 SKIPPED)
```

### 2.3 Mathematical & Root Cause Explanation
1. **Phases 5–8 Cumulative Baseline:**
   `Phase 5 (18) + Phase 6 (8) + Phase 7 (15) + Phase 8 (23) = 64 tests`.
   The earlier report of 64 cumulative tests for Phases 5–8 was **100% mathematically and physically accurate**.
2. **Phase 8 Standalone Test File:**
   `tests/test_v2_phase8.py` contains exactly **23 tests** across 5 test classes.
3. **Phase 2 Label Reconstruction File:**
   `tests/test_v2_label_reconstruction.py` contains exactly **18 tests** across 8 test classes.
4. **The Reporting Transposition Error:**
   When compiling the Phase 9 markdown report, the author combined Phase 2 (18 tests), Phases 5–8 (64 tests), and Phase 9 (68 tests):
   `18 + 64 + 68 = 150 tests`.
   In the markdown table, the author inadvertently entered **14** instead of 18 for label reconstruction (-4) and **27** instead of 23 for Phase 8 (+4). The sum remained 150.
5. **Integrity Conclusion:**
   Zero tests were added, removed, deleted, or bypassed. The discrepancy is purely a clerical transposition in the markdown table of the Phase 9 report. The codebase and test suite are completely intact and 150/150 tests pass cleanly in 21.61 seconds.

### 4.2 Special Modality Verifications
1. **Retina Multilabel Formulation:**
   Verified that the Retina pipeline applies 8 independent sigmoids:
   $$P(Y_k = 1 \mid X) = \sigma(z_k) = \frac{1}{1 + e^{-z_k}}$$.
   Sum of probabilities across labels equals `2.7634` (strictly not summing to 1.0, proving no softmax is applied). Decisions are evaluated independently against per-label optimal thresholds:
   `normal: 0.44`, `diabetic_retinopathy: 0.36`, `glaucoma: 0.66`, `cataract: 0.93`, `amd: 0.93`, `hypertension: 0.86`, `pathological_myopia: 0.92`, `other_abnormality: 0.32`.
2. **Brain CT and Ultrasound Cross-Validation Mapping:**
   Brain CT (200 cases) and Breast Ultrasound (780 cases) were developed using 5-fold cross-validation. For operational deployment in Phase 9, `fold_0/best_model.pt` is deployed as the canonical checkpoint. Generalization metrics reported in Phase 6 represent cross-validation aggregations, whereas runtime inference executes on Fold 0 exclusively. This restriction is cleanly documented in `MODALITY_SETTINGS[mod]['cv_limitation']`.
3. **Preprocessing Consistency (Audit 4):**
   Audited `training/v2_baseline/transforms.py`, `dataset.py`, `pipeline_v2/validator.py`, and `ood_detection/modality_adapter.py`. All seven modalities use identical deterministic evaluation transforms:
   - Pixel conversion: 3-channel RGB (grayscale images auto-converted to 3 identical channels).
   - Spatial resolution: Resized to $(224, 224)$ via bilinear interpolation.
   - Tensor conversion: Pixel values scaled to $[0.0, 1.0]$.
   - Normalization: ImageNet statistics $\mu = [0.485, 0.456, 0.406]$, $\sigma = [0.229, 0.224, 0.225]$.
   - Result: 100% consistency between training and inference preprocessing.

### 5.2 Quality Gate Precedence Hierarchy
The quality gate decision logic enforces strict short-circuiting precedence:
1. `GATE_INPUT_VALIDITY` -> `REJECTED_INVALID_INPUT`
2. `GATE_MODALITY_VALIDITY` -> `REJECTED_UNSUPPORTED_MODALITY`
3. `GATE_MODEL_AVAILABILITY` -> `INFERENCE_ERROR`
4. `GATE_FINITE_OUTPUTS` -> `INFERENCE_ERROR`
5. `GATE_CALIBRATION_STATUS` -> `FLAGGED_FOR_REVIEW`
6. `GATE_OOD_CHECK` -> `REJECTED_OOD` (Abstention enforced by default)
7. `GATE_ANOMALY_CHECK` -> `REVIEW_REQUIRED_ANOMALY` (Review flag)
8. `DEFAULT` -> `ACCEPTED_FOR_MODEL_OUTPUT`

**Anomaly Representation Safeguard:**
When an in-distribution sample deviates from normal reference centroids (e.g. Brain CT hemorrhage case `000.png` or Ultrasound malignant case `benign (1).png`), the gate assigns `REVIEW_REQUIRED_ANOMALY` with explanation: *"Potential morphological deviation from normal reference state."* Anomaly scoring explicitly does NOT assign a disease diagnosis or claim confirmation of pathology.

### 6.2 Privacy & Provenance Review
Audit logging was evaluated in `pipeline_v2/audit_logger.py`:
- **Patient Identifiers:** Raw patient IDs are never stored. If a patient identifier is submitted (e.g. `PATIENT-SECRET-12345`), it is transformed using one-way SHA-256 hashing to a truncated pseudonym (e.g. `HASH-a8b2c4e1`).
- **Raw Image Data:** Raw image pixel arrays and file bytes are never stored in the audit trail. Only the 64-character SHA-256 digest of the image bytes is recorded.
- **Traceability:** Records include timestamp (ISO 8601 UTC), pipeline version (`V2.0-Phase9`), model identifier (`resnet18`), checkpoint path, gate status, OOD score, anomaly score, and calibration identifier.

## 7. Scientific Claims and Known Limitations (Audit 7)

### 7.1 Separation of Concepts
The codebase, configuration, and reports enforce rigorous theoretical distinctions:
- **Validation vs. Test Data:** All temperature scaling parameters, Retina thresholds, and OOD operating thresholds were fitted strictly on validation splits. Test splits were evaluated once with frozen parameters.
- **Classification vs. Calibration:** Calibration quality is measured via Expected Calibration Error (ECE) and Brier Score, distinguished from classification accuracy and macro-AUC.
- **OOD Detection vs. Disease Diagnosis:** OOD detection tests whether an input belongs to the trained imaging domain. An in-distribution input flagged with an anomaly score indicates deviation from a healthy normal pattern, not a definitive diagnosis.

### 7.2 Documented Scientific Limitations Verified
All five known scientific limitations remain documented in the repository reports:
1. **Small CT Evaluation Sample:** The Brain CT dataset contains 200 total slices (12 normal, 8 hemorrhage in the test partition). While cross-validation AUROC is high, wider clinical confidence intervals exist.
2. **Weak Retina Normal-Reference Anomaly Separation:** In Phase 8, within-distribution anomaly detection for Retina achieved an AUROC of `0.5903` and sensitivity of `26.1%` at 90% specificity. This is documented: multi-label retinal disease features overlap with normal fundus appearance in feature space.
3. **Histopathology Tile-Level Correlation:** The LC25000 histopathology dataset consists of cropped image tiles without patient or slide identifiers. Tiles from the same histological slide may appear across splits, creating potential correlation.
4. **Synthetic vs. Real-World Domain Shifts:** Phase 8 benchmarked OOD detection against cross-modality foreign inputs and synthetic noise/blur. Clinical distribution shifts (e.g. scanner manufacturer differences, slice thickness variation) require multi-center clinical cohorts.
5. **Cross-Validation Runtime Model:** Brain CT and Ultrasound utilize Fold 0 checkpoints at runtime. Generalization estimates in Phase 6 reflect 5-fold cross-validation, while runtime execution evaluates on the Fold 0 model exclusively.

### 7.3 Unsupported Claims Flagged
- **Flagged Item (`REC-03` — Severity: LOW):** In legacy V1 documentation (`docs/PROJECT_REPORT.md`, line 64), the phrase *"Build a production-ready REST API and web dashboard for direct clinical use"* appears. This legacy text was drafted prior to V2.0 hardening. While all V2.0 reports contain prominent investigational research prototype disclaimers, `docs/PROJECT_REPORT.md` should be amended to eliminate any reference to direct clinical use.
